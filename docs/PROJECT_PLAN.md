# halo_server 项目规划

## 项目目标

建立一个可审计、可重复执行的云服务器统一部署与运维仓库。每项服务以独立模块维护，同时通过统一入口完成安装、更新、状态检查和必要的回滚操作。

## 设计原则

- **模块隔离**：每个服务拥有独立文档、配置模板、脚本和测试。
- **配置与代码分离**：真实环境配置、密钥和客户端凭据不得进入 Git。
- **安全默认值**：部署脚本不得静默覆盖现有服务配置；高风险操作需要显式确认。
- **幂等与可恢复**：重复执行应保持结果一致，变更前应保留必要备份。
- **先验证后应用**：代码合并和服务器部署前执行静态检查及模块测试。
- **最小权限**：服务器拉取代码使用只读凭据，运行时权限按模块需要授予。

## 规划结构

## 阶段规划

### 阶段一：仓库与 WireGuard 基线

- 建立 GitHub 私有仓库和 `main` 主分支。
- 完成 WireGuard 首次安装、客户端增删、状态检查和基础测试。
- 在真实 Ubuntu/Debian 云服务器完成端到端验证。

### 阶段二：统一部署入口

- 增加根目录 `deploy.sh`。
- 为模块定义统一的 `install`、`update`、`status`、`uninstall` 接口。
- 增加配置检查、执行预览和备份机制。

### 阶段三：质量与发布

- 引入 ShellCheck 和自动化测试。
- 使用版本标签发布稳定版本。
- 服务器通过只读 Deploy Key 拉取固定标签或明确提交。
- 对网络类变更保留人工审批，避免自动部署导致 SSH 失联。

### 阶段四：扩展服务模块

- 反向代理与 TLS 证书管理。
- 主机及服务监控。
- 配置、数据与恢复验证型备份。
- 基础安全加固和审计。

## 部署策略

初期采用人工触发：服务器执行 `git pull --ff-only`，验证变更后再运行指定模块。项目稳定后，可使用 GitHub Actions 做测试和发布，但生产部署继续保留环境审批。

## 完成标准

一个模块进入“稳定”状态前，应满足：

1. 支持目标操作系统并明确版本范围；
2. 提供配置模板和完整操作文档；
3. 不向仓库写入任何密钥或真实环境配置；
4. 具备静态检查和可重复运行的基础测试；
5. 在测试服务器完成安装、更新、重启和故障恢复验证；
6. 明确卸载或回退方法。
